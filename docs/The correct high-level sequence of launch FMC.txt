The part you correctly identified as missing

The important section is this:

Provider Discovery
       ↓
Provider Health
       ↓
Model Discovery
       ↓
Model Normalization
       ↓
Model Validation
       ↓
Active Model Filtering
       ↓
Capability Filtering
       ↓
Model Routing
       ↓
UI

The UI should not be responsible for deciding which models are actually usable.

For example, Arena/OpenRouter/Groq/etc. may return a model, but that doesn't automatically mean Free Model Club should display it as available.

A model may be:

disabled
temporarily unavailable
API-key unavailable
outside quota
rate-limited
incompatible with the requested endpoint
lacking tool/function calling
lacking vision
unsuitable for coding
deprecated
provider-disabled
context window too small
temporarily unhealthy

Therefore you need a Model Eligibility Pipeline.

Recommended
Raw Provider Models
        ↓
Normalize
        ↓
Validate
        ↓
Provider Status
        ↓
API-Key Status
        ↓
Model Status
        ↓
Quota Status
        ↓
Capability Detection
        ↓
Compatibility Check
        ↓
Active Model Filter
        ↓
Eligible Model Registry
        ↓
Routing Engine

And this should run before the UI consumes the model list.

And one more thing

Theme, UI and model filtering should not be mixed into the same startup sequence.

For example:

Theme Manager
     ↓
UI Theme State

is independent of:

Provider
 ↓
Model
 ↓
Eligibility

The UI simply consumes the already prepared application state.

That gives you:

Database → Services → State → UI

rather than:

UI → Database → API → filter → UI → API → filter → UI

which eventually becomes spaghetti with a user interface attached. 🍝
